# Architecture

This document describes how BattleLog is laid out, the conventions new code should follow, and the non-obvious design decisions worth knowing before extending the service.

## Stack

- **Runtime**: Node 24, TypeScript (ES2022, NodeNext modules)
- **HTTP**: [Hono](https://hono.dev/) via `@hono/node-server`, OpenAPI surface via `@hono/zod-openapi`
- **ORM**: [Drizzle](https://orm.drizzle.team/) (`drizzle-orm` + `drizzle-kit`)
- **Database**: Postgres 16 with the [PostGIS](https://postgis.net/) extension
- **Validation**: [Zod](https://zod.dev/) (request/response schemas double as OpenAPI definitions)
- **Logging**: [pino](https://getpino.io/) + `hono-pino`, stdout in dev, plus `pino-opentelemetry-transport` in prod
- **Observability**: OpenTelemetry (`@opentelemetry/auto-instrumentations-node`), bootstrapped from `src/instrumentation.ts`
- **Config**: [varlock](https://varlock.dev/) — `.env.schema` is the single source of truth, generates typed `ENV` at build time
- **Lint/format**: [Biome](https://biomejs.dev/)
- **Tests**: [Vitest](https://vitest.dev/)

## Top-level layout

```
.
├── src/
│   ├── app.ts                 # Hono app factory: CORS, logger, swagger, static, routes
│   ├── index.ts               # Server entrypoint (port binding, lifecycle)
│   ├── instrumentation.ts     # OTel SDK bootstrap (imported via --import in prod)
│   ├── env.d.ts               # Generated by varlock typegen — DO NOT EDIT
│   ├── db/                    # Drizzle client, schema, migration runner
│   ├── routes/<feature>/      # HTTP surface for a feature
│   ├── services/<feature>/    # Domain logic for a feature
│   ├── lib/                   # Cross-cutting utilities (logger, client-ip, uploads)
│   └── middleware/            # Global Hono middleware (rate-limit, …)
├── drizzle/                   # Generated migrations + meta snapshots (committed)
├── scripts/                   # Dev/seed utilities (fake-events, seed)
└── .env.schema                # Single source of truth for runtime config
```

## Per-feature convention

A "feature" (e.g. `events`) is split into two parallel folders:

| File | Role |
|---|---|
| `routes/<feature>/<feature>.routes.ts` | Route registration: maps HTTP verbs/paths to handlers, wires per-route middleware (rate-limits, auth) |
| `routes/<feature>/<feature>.apiSchema.ts` | Zod request/response schemas — these are the OpenAPI source of truth |
| `routes/<feature>/<feature>.handlers.ts` | Thin HTTP adapters: parse → call service → shape response |
| `services/<feature>/<feature>.service.ts` | Domain orchestration; the public surface other features consume |
| `services/<feature>/<feature>.dbSchema.ts` | Drizzle table definition for the feature (re-exported from `src/db/schema.ts` if shared) |
| `services/<feature>/<feature>.filter.ts` | Query-building helpers (predicates, ordering, pagination) |
| `services/<feature>/<feature>.emitter.ts` | Event-bus / SSE / pub-sub helpers when the feature streams |

Not every feature needs every file. The `events` feature is the canonical example — copy it when adding a new resource.

**Tests** live next to source as `*.test.ts`. The TypeScript build excludes them; Biome includes them.

## Request flow

Using `POST /api/v1/events` as the walkthrough:

1. **`app.ts`** mounts `eventRoutes` under both `/api` and `/api/v1` (versioned routing, both kept live so unversioned clients keep working).
2. **`routes/events/events.routes.ts`** applies `strictRateLimit` (writes) or `generalRateLimit` (reads) and dispatches to a handler.
3. **`routes/events/events.handlers.ts`** validates the body against the Zod schema from `events.apiSchema.ts`, calls into `events.service.ts`, and serializes the result.
4. **`services/events/events.service.ts`** owns the domain logic — version-chain bookkeeping, PostGIS coordinate handling, audit fields.
5. **`services/events/events.filter.ts`** builds Drizzle queries (including PostGIS `ST_DWithin`-based geo filters).
6. **`services/events/events.emitter.ts`** fans changes out to subscribers of `GET /events/stream`.

## Data model: append-only versioned events

The `events` table is **append-only with explicit version chains**. Three ID columns describe the chain:

- `id` — unique per row (i.e. per version)
- `eventId` — stable logical event identifier, inherited unchanged across versions
- `updateFor` — points to the previous version's `id`; `null` on the root row, `UNIQUE` so concurrent updates fail with a constraint violation rather than forking history

A check constraint enforces that root rows satisfy `eventId = id`. The foreign key `(updateFor, eventId) → (id, eventId)` makes it impossible to "graft" a version onto a different logical event.

Geospatial coordinates are stored as a PostGIS `geometry(point, 4326)` (WGS84) and indexed with GiST. Drizzle reads/writes `[lng, lat]` tuples — the API layer is responsible for `{ lat, lng }` ↔ tuple conversion at the boundary.

Two NATO/Hybrid-CoE taxonomies live in the schema:

- **Admiralty Code** (NATO AJP-2.1 / STANAG 2511) — source reliability `A`–`F` and information credibility `1`–`6`
- **Hybrid CoE domains** — multi-valued array of hybrid-threat domains (information, cyber, military, …)

Both are exposed as enums / arrays in the API; see `src/db/schema.ts` for the canonical values.

## API versioning

Routes are mounted twice: at `BASE_URL/api/*` and `BASE_URL/api/v1/*`. Both point to the same handlers today; the duplicate path exists so a future `/api/v2` can be introduced without breaking existing clients. Keep new routes registered through the same loop in `app.ts`.

## Configuration

`varlock` reads `.env.schema` at process start, validates `.env` against it, and exposes a typed `ENV` object (`varlock/env`). The schema file's `@generateTypes` annotation regenerates `src/env.d.ts` whenever the schema changes; never edit `env.d.ts` by hand.

Defaults differ per environment via `if(forEnv(development), …)` — used for `DATABASE_URL` (points at local compose Postgres in dev) and `USE_SWAGGER` (Swagger UI enabled in dev only).

## Observability

`logger` (in `src/lib/logger.ts`) is the single pino instance, exported into both the app middleware and ad-hoc call sites. It writes to stdout in all environments and adds the `pino-opentelemetry-transport` stream when `NODE_ENV=production`. **Do not write log files** — containerized deployments expect stdout/stderr only.

When `OTEL_EXPORTER_OTLP_ENDPOINT` is set, `src/instrumentation.ts` boots the OTel SDK with auto-instrumentations. In production the entrypoint uses `node --import ./dist/instrumentation.js` so traces capture cold-start work too.

## Cross-cutting concerns

- **Rate limiting** (`src/middleware/rate-limit.ts`) keys off the client IP. Behind a reverse proxy, configure `BL_TRUST_PROXY_HOPS` so XFF parsing peels the right number of proxy hops (0 = ignore XFF entirely).
- **mTLS / Rasenmaeher integration** is opt-in: set `RM_API_ENABLED=true` to mount `/rmapi/*`, plus `RM_MTLS_ENFORCE` to require the proxy-injected client-cert header. Local dev keeps this off because direct localhost access has no proxy.
- **Uploads** are served from `./uploads` (cwd-relative, so the container volume at `/usr/src/app/uploads` lines up). Filenames are UUIDv7 to keep them sortable and avoid collisions.
- **SPA fallback** — `app.use("*", serveStatic({ root: "./public" }))` is mounted last so it only serves frontend assets when no API route matched.

## Supply-chain hardening

[`.npmrc`](./.npmrc) sets `minimum-release-age=20160` (14 days) so newly-published package versions are refused until they age — a defense against compromised maintainer accounts and typosquats caught within days of publish. [`pnpm-workspace.yaml`](./pnpm-workspace.yaml) explicitly allows post-install build scripts for `esbuild` and `protobufjs` only; pnpm blocks all other dependency lifecycle scripts by default.

## Adding a new feature

1. Create `src/services/<feature>/<feature>.dbSchema.ts` (or extend `src/db/schema.ts`) and run `pnpm db:generate` to produce a migration.
2. Add `src/services/<feature>/<feature>.service.ts` with the domain operations.
3. Define request/response shapes in `src/routes/<feature>/<feature>.apiSchema.ts`.
4. Wire handlers in `<feature>.handlers.ts` and register routes in `<feature>.routes.ts`.
5. Mount the router in `src/app.ts` under both `/api` and `/api/v1`.
6. Add `*.test.ts` co-located with the new code.
